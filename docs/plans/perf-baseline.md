# Замер производительности и оценка ёмкости (baseline)

> **Дата замера:** 2026-08-16. Среда: локальный Docker-стек (прод-конфигурация),
> 2 активные гильдии, нагрузка синтетическая. Числа — ориентир для выбора VPS и
> приоритетов оптимизации, не гарантия. Связано: [ADR-002](../adr/ADR-002-renderer-isolated-service.md)
> (renderer), [Poposya_improvement_plan](Poposya_improvement_plan.md).

> **Обновление 2026-08-16 (после оптимизаций A2/A3/A4/A5/B2/B1):** повторный замер
> той же методикой (120 distinct-рендеров @conc8 + 840 к api). Ниже — раздел
> «Повторный замер». Кратко: renderer перестал быть узким местом — RAM 507→82 МБ
> (near-OOM устранён), карточка 3.5–6 с → ~140 мс, образ 2.15 ГБ→274 МБ (Chromium→
> librsvg, B1). См. [scale-300-guilds.md](scale-300-guilds.md).

## Методика

- **Снятие:** `docker stats --no-stream` по всем контейнерам, семплинг ~1.5 с,
  пики за окно ~40 с.
- **Нагрузка renderer:** POST /render изнутри `bot`-контейнера (renderer на
  internal-сети, наружу не публикуется; доступен только боту), 2 волны по 60
  рендеров, concurrency 8; карточка — реалистичный glassmorphism (blur/градиенты/
  свечение), 600×380 @ scale 2.
- **Нагрузка api:** флуд `GET /api/health` через nginx `:8443`, 20 параллельно,
  840 запросов за окно.
- **Музыка:** реальный плейлист в Discord (1 стрим), запущен вручную —
  синтетически голосовой трафик не воспроизвести.
- **Не нагружалось синтетически:** Discord-gateway события, AI (Groq был
  недоступен — HTTP 403 в логах на момент замера), несколько одновременных
  голосовых. Эти драйверы оценены, а не измерены.

## Пики под совмещённой нагрузкой

Музыка (1 стрим) + 120 рендеров @ conc 8 + 840 запросов к api через nginx:

| Контейнер | Пик CPU | Пик RAM | mem_limit | % лимита |
|---|---:|---:|---:|---:|
| **renderer** (Chromium) | **392%** (~4 ядра) | **507 MB** | 512 MB | **99%** 🔴 |
| bot (ffmpeg + рендер-клиент) | 88% (~1 ядро) | 221 MB | 512 MB | 43% |
| api | 41% | 99 MB | 256 MB | 39% |
| db (Postgres) | 8% | 82 MB | 2048 MB | 4% |
| web (nginx) | 10% | 17 MB | 128 MB | 13% |
| **Σ пик RAM** | | **~0.95 GB** (+WARDEN ~0.04 → **~1 GB**) | | |

Renderer в холоде 37 MB, тёплый (после 6 рендеров) 323 MB, под нагрузкой 507 MB.
Одна glassmorphism-карточка рендерится **3.5–6 с** (software-компоновка blur без GPU).

## Что во что упирается

- **Связывающий ресурс — CPU (ядра), не память.** Пик RAM всего ~1 GB; Postgres
  и nginx почти не шевелятся (БД крошечная).
- **renderer/Chromium — доминирующий потребитель:** под 8 одновременными
  рендерами упёрся в лимит памяти (507/512 MB — почти OOM) и сожрал ~4 ядра.
- **Музыка (ffmpeg):** ~⅓–½ ядра + 40–80 MB на активный стрим (оценка: 88% бота
  включали и роль рендер-клиента — цифра консервативна).
- **AI:** сеть/деньги, не локальный CPU; ограничен внешним rate-лимитером.

## Модель ёмкости

Нагрузку задаёт **одновременная активность**, не общее число гильдий:

> активных гильдий ≈ (свободные ядра ÷ стоимость на стрим) ÷ доля одновременно активных

Доля «одновременно с музыкой»: лёгкий профиль ~3–5%, типичный ~8–12%, музыкальный ~20–30%.

**4 vCPU / 4 GB (текущий код, Chromium):** ~2.5–3 ядра на музыку (1 ядро в резерв
под рендер-бёрсты) → ~7 одновременных стримов.

| Профиль | Активных гильдий |
|---|---|
| Лёгкий (~4%) | ~150–200 |
| Типичный (~10%) | ~60–80 |
| Музыкальный (~25%) | ~30 |

**2 vCPU / 2 GB (после оптимизации renderer'а):** ~1.5 ядра на музыку → ~4 стрима.

| Профиль | Активных гильдий |
|---|---|
| Лёгкий (~4%) | ~80–100 |
| Типичный (~10%) | ~40 |
| Музыкальный (~25%) | ~15 |

## Рекомендации по VPS

- **Сейчас:** 4 vCPU / 4 GB / 60–80 GB SSD (запас под рендер-бёрсты); либо
  2 vCPU / 4 GB, если рендеры редки. RAM не лимит (пик ~1 GB), решают ядра и диск
  (образы ~5 GB, из них renderer 2.15 GB).
- **После оптимизации:** 2 vCPU / 2 GB / 40 GB — комфортно, тир в 1.5–2× дешевле.

Та же методика: 120 **distinct**-рендеров @conc8 (мимо кэша — реальная
растеризация) + 840 к api. Стек после A2/A3/A4/A5/B2/B1.

| Контейнер | Пик CPU | Пик RAM | Было (Chromium) |
|---|---:|---:|---|
| **renderer** (librsvg) | 298% (кап admission=3) | **82 MB / 256** | 392% / **507 MB (near-OOM)** |
| bot | 63% | 122 MB | 88% / 221 MB |
| api | 0.3%* | 81 MB | 41% / 99 MB |
| db (Postgres) | 0.6% | 59 MB | 8% / 82 MB |
| web (nginx) | 2.3% | 13 MB | 10% / 17 MB |

\* api-флуд (840 @ ~1200/с, все ok) уложился в ~0.7 с — сэмплер (шаг ~2 с) пик
недобрал. Волна рендеров: **120 × 200, все MISS, 0 отказов (503), 0 OOM/рестартов.**

**Итоги:** одна карточка **3.5–6 с → ~140 мс**; renderer RAM **507→82 MB**
(near-OOM устранён); образ renderer **2.15 GB → 274 MB**; пул БД 60→30, Postgres
тюнингован (B2). **Renderer перестал диктовать RAM/диск/VPS-тир** — связывающий
ресурс остался один: CPU на одновременную музыку (PCM, ~0.4 ядра/стрим — не
менялось по решению владельца). Под 300 активных с музыкой ориентир — 8 vCPU / 8 GB
(типичный профиль), см. [scale-300-guilds.md](scale-300-guilds.md).

## Приоритеты оптимизации (по отдаче)

1. ✅ **Renderer: headless-Chromium → librsvg (SVG).** Сделано (B1): пик RAM
   507→82 MB, карточка 3.5–6 с→~140 мс, образ 2.15 GB→274 MB, риск OOM снят.
2. ❎ **Музыка через Opus-copy** — рассмотрено, **отклонено** владельцем (оставлен
   PCM ради идеальной живой громкости; см. scale-300-guilds.md).
3. ✅ **Дедуп образа bot/api** (A5) — один образ `poposyap-app`.
4. ✅ **Ужать/тюнинговать Postgres** (B2) — конфиг задан, mem_limit оставлен 2 GB
   как VPS-решение.
5. ✅ **Урезать пул БД** (A4) — 10+20 → 5+10 (60→30 коннектов).

## Оговорки

- Стоимость «⅓–½ ядра на стрим» — из одного замера с примесью рендер-клиента;
  чистую цифру даст замер CPU бота при одном стриме без другой нагрузки.
- Числа ёмкости доминируются **допущением о concurrency** — при известной доле
  активных гильдий подставить в формулу выше.
- Потолок при высоком числе гильдий сместится с CPU на **RAM/диск Postgres**
  (рост данных), тогда важнее память и SSD, а не ядра.
