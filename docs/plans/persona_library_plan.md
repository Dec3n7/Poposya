# План: Библиотеки персон (Persona Libraries) — рекомендуемый вариант

## 0. Философия: тонкий срез вперёд

Исходная задача — заказчик даёт свой промпт (и лицо), грузим в панель, назначаем
серверу; фразы правятся быстро. Это **не** требует CMS/i18n-движка. Делаем ровно
столько, чтобы закрыть задачу и не закопаться, а «максимальную гибкость» вводим
**по факту спроса**, а не заранее (см. §14). Что вырезал из максимум-версии и почему —
в §15.

**Принцип:** дефолты = текущая «Попося» (в коде), в БД только override, hot-reload без
рестарта — переиспользуем проверенный паттерн `guild_settings`.

## 1. Объём

**В v1:**
- Именованные библиотеки-персоны (создать / **дублировать** / удалить). Без
  наследования — «дублировать из» вместо `parent` (проще, без ловушек версий).
- Промпт персоны = **цельный** редактируемый текст (базовый + chime), без нарезки на
  секции.
- **Каталог ВСЕХ пользовательских строк рантайма** — весь текст, что видит юзер: и явный
  «голос» (приветствия/находки/…), и **inline-строки в f-строках** («Добавила:», «Нашла
  5 — выбери трек:»), и подписи/кнопки эмбедов. Всё **персона-скоупное** (родовые глаголы
  и тон = часть личности: «Добавил**а**» → «Закинул»). Правятся построчно (было→стало),
  find-replace, режим на блок, защита плейсхолдеров. Дефолты в реестре, в БД — только
  override, поэтому НЕ деление на «глобальный vs персона»: одна библиотека = весь текст.
- **Мягкая личность**: имя-в-тексте, эмодзи-подпись, accent-цвет, Discord-presence.
- Назначение персоны серверу (hot-reload).
- Экспорт/импорт библиотеки в JSON («заказчик прислал — я загрузил»).
- **Роль оператора**: всем этим управляет только владелец бота.

**НЕ в v1 (бэклог по спросу, §14):** наследование, версии/откат, превью-генерация,
редактирование **слэш-команд** (имена/описания — внешняя зависимость от Discord,
ре-синк), per-guild override, полное владение персоной bot-профилем (аватар/ник),
мультиязычность.

## 2. Доменная модель (минимальная)

```
Persona
  id, name, is_default          # встроенная «Попося» = is_default, неудаляема
  prompt, chime_prompt          # цельные тексты (с {{переменными}})
  attributes (JSON)             # имя-в-тексте, подпись-эмодзи, accent, presence[]
  created_at, updated_at

PersonaPhrase                    # override фразы каталога
  persona_id, key               # key из PHRASE_SPECS ("activity.welcome" и т.п.)
  value (JSON)                  # str | list[str] | dict[str,str]; NULL=дефолт, ''=«молчать»
  mode                          # ai_then_static (умолч.) | static | silent

GuildPersona                     # назначение
  guild_id (PK), persona_id
```

**Реестры (дефолты в коде):** `PHRASE_SPECS` — key, category, kind (str/list/dict/
template), default (текущая Попося), placeholders, allowed_modes, «каркас» (см. §6).
Дефолты в БД не дублируем. После миграции поведение = текущее (по значениям).

Резолв **в 2 уровня**: `persona_phrases[persona,key]` → `PHRASE_SPECS.default`.
(Один уровень override — как у настроек. Никаких цепочек наследования в v1.)

## 3. Рантайм: `PersonaService`

`src/domain/persona/` + `src/application/persona/` + `src/infrastructure/persona_service.py`:
- `load_all()` на старте (персоны, фразы, назначения → кэш).
- `for_guild(gid)` / `phrase(gid, key, **vars)` / `render_prompt(gid, vars)` — sync из
  кэша (горячие пути когов).
- `reload()` по NOTIFY `poposya_personas` (панель изменила → бот перечитал).
- CRUD + set-phrase/mode/attribute + set-prompt + assign + import/export (API-процесс:
  запись в БД + NOTIFY).
- Wiring: `build_root_container` (бот) и `assemble_container` (API), рядом с
  `guild_settings`; NOTIFY-листенер — аналог `settings_listener`.

## 4. Что выносим (инвентарь → `PHRASE_SPECS`)

- **Промпты**: `poposya_v1.md` → `Persona.prompt`; `poposya_chime_decision_v1.md` →
  `chime_prompt` (файлы остаются как сид дефолта, не рантайм-источник).
- **Вшитое в `ai_chat/service.py`**: `_BRUSH_OFFS`, инструкции резюме/заметок,
  `_survey_block` («любимое лето»), `_memory_block`, хвосты `comment_on_event`/
  `freeform_remark`/`_generate_chime`/`_build_system_prompt`, имя+подпись.
- **Именованные константы когов**: `activity` (welcome/farewell/album + AI-инструкции),
  `finds` (openers/fail/success.*/gift{}/walk_*), `secret_room` (dm/room_welcome),
  `introduce` (season_replies{}/done_replies[]), `ai_chat`-ког (error_replies),
  `music/service` (fail_phrases), `cinema` (инструкции комментариев), `tempvoice/phrases.py`.
- **Inline-строки в f-строках/эмбедах (важно, я их раньше проглядел)** — весь текст, где
  бот «говорит», прямо в логике когов: «Добавила: {track}», «Нашла N — выбери трек:»,
  подтверждения, подписи полей эмбедов, надписи кнопок, тексты вида «Только вы видите
  это сообщение». Их тоже в каталог (родовые глаголы = голос). ~300 строк в 23 файлах —
  вынимаются волнами по когам (см. §11 P4).
- **Мягкая личность**: имя, ✂️👁🖤, accent (`_EMBED_COLOR`), presence-строки.
- **НЕ трогаем в v1**: слэш-команды (имена/описания — бэклог, ре-синк Discord); аватар/
  ник/баннер (остаются в `bot_profile`); правила сервера `fun._RULES_TEXT`/`_TOPICS` и
  числовые параметры поведения — это `guild_settings`, не персона; структурные енумы
  анкеты (`_GENDER_OPTIONS` и т.п.).

## 5. Личность без конфликта источников

v1 персона несёт **мягкую личность**: имя-в-тексте, подпись, accent, presence. Их
меняет персона (accent — в эмбедах через резолв; presence — переустановка при
назначении). **Аватар/ник/баннер НЕ трогаем** — остаются в текущем per-guild
`bot_profile` как есть. Так избегаем двух источников правды и не переписываем рабочую
фичу. Полное владение профилем (лицо меняется вместе с персоной) — бэклог §14, когда
понадобится.

## 6. Рефакторинг когов и `ChatService`

- Простые строки — через `persona.text(gid, key, **vars)` (замена литерала:
  `f"Добавила: {t}"` → `persona.text(gid, "music.added", track=t)`). AI-блоки — через
  `render_block(gid, key, ai_fn=None, **vars)`: резолвит значение+режим и разруливает
  `ai_then_static`/`static`/`silent` + деградацию. Коги/сервис вызывают их вместо
  констант и литералов; константы удаляются.
- **Гвард против протухания (обязателен):** тест/линт ловит новые user-facing литералы
  вне `persona.text(...)`/`render_block(...)` (эвристика: строковые литералы в `.send(`,
  `Embed(`, `add_field(`, `CommandError(`, `label=` без обёртки). Иначе после выноса
  ~300 строк новые фичи снова начнут хардкодить, и каталог разъедется.
- **Каркас — прагматично, не догматично**: для AI-инструкций система всегда добавляет
  жёсткий формат-хвост («верни ТОЛЬКО текст, одно сообщение, без @»), заказчик правит
  «подачу» (тон). Не пытаемся резать каждую фразу на два — только там, где реально есть
  и AI-инструкция, и формат. Плюс валидация плейсхолдеров при сохранении.
- `ChatService`: `persona.render_prompt(gid, vars)` вместо файла-шаблона; inline-куски
  → `persona.phrase(...)`.
- Wiring в когах — рядом с `guild_settings`.

## 7. Роль оператора

- Конфиг `web_operator_ids: list[int]` (Discord-ID) + зависимость `require_operator`
  (`session.user_id ∈ web_operator_ids`) — под ней ВСЕ роуты персон.
- `/auth/me` отдаёт `is_operator` → фронт прячет вкладку «Персона» у не-операторов.
- Серверные админы персону не трогают вовсе.

## 8. API `src/api/routers/personas.py` (под `require_operator`, аудит `persona.*`)

- `GET/POST /personas`, `POST /{id}/duplicate`, `PATCH/DELETE /{id}`.
- `GET/PUT /{id}/prompt` · `PUT /{id}/chime_prompt`.
- `GET /{id}/phrases` (категории→ключи→{default,value,mode,is_override,placeholders,
  allowed_modes}) · `PUT/DELETE /{id}/phrases/{key}` · `PUT …/{key}/mode`.
- `GET/PUT /{id}/identity` (имя/подпись/accent/presence).
- `GET/PUT /guilds/{gid}/persona` (назначение).
- `POST /{id}/replace {find, replace, dry_run}` (find-and-replace по фразам).
- `GET/POST /{id}/export|import` (JSON библиотеки — заменяет и «версии», и перенос).

Запись → БД + pg_notify → бот перечитал без рестарта.

## 9. Панель — вкладка «Персона» (только оператор)

1. Библиотека сервера: активная персона (дропдаун) + Создать/Дублировать/Импорт/Экспорт;
   бейдж «на N серверах».
2. Промпт: две textarea (`prompt`, `chime_prompt`), подсказка `{{переменных}}`, «сброс
   к дефолту».
3. Фразы: категории → строки inline-правки (было→стало), селектор режима, badge
   «изменено», «сбросить»; списки/словари — добавить/удалить/править; подсветка
   плейсхолдеров; **глобальный find-and-replace** с предпросмотром.
4. Личность: имя, подпись, accent, presence-статусы.
Сохранение по элементу (PUT одного ключа).

## 10. Миграции
- `0031_personas`: `personas`, `persona_phrases`, `guild_persona`.
- Сид «Попоси» (`is_default`) — атрибуты заданы; `prompt`/`chime_prompt` из файлов;
  фразы в БД пустые (дефолты в реестре).
- Тест-сверка `PHRASE_SPECS` (полнота, плейсхолдеры, режимы) — аналог
  `test_guild_config_schema`.

## 11. Фазы (каждая деплоится, Попося не ломается)

- **P1 — Каркас.** Миграция 0031, домен/репо/сервис, `PHRASE_SPECS` (промпт + 1-2
  категории), резолв, сид, роль оператора, NOTIFY, wiring. Поведение не меняется.
- **P2 — Промпт из библиотеки + назначение.** `ChatService` рендерит промпт персоны
  per-guild. Панель: редактор промпта, назначение, экспорт/импорт. → **заказчик уже
  даёт свой промпт.**
- **P3 — Мягкая личность.** Атрибуты (имя/подпись/accent/presence) + применение presence.
- **P4 — Весь текст в каталог (самая ёмкая, ~300 строк).** Ввести `persona.text()` +
  `render_block()` + гвард; вынести ВСЕ user-facing строки (именованные константы +
  inline f-строки типа «Добавила:») волнами по когам (activity → finds → secret_room →
  introduce → ai_chat → music → cinema → moderation/общее), режим на блок, панель-
  редактор + find-replace. Чекпоинт после каждой волны — не «всё разом».

Уже после **P2–P3** закрыт запрос «дал промпт и лицо — назначил»; **P4** закрывает
«поменять любую фразу бота» («Добавила:» → «Закинул вам»). P4 можно дробить и катить
по одному когу — каждая волна самостоятельна.

## 12. Тестирование
`PHRASE_SPECS` (полнота/плейсхолдеры/режимы) · `PersonaService` (резолв, reload, CRUD,
import/export) · репо/миграция (uow_factory) · коги (`render_block`: режимы+деградация,
мок `phrase`) · API (CRUD, режим, find-replace, назначение) · веб (`tsc` через Docker).

## 13. Риски (актуальные для лин-версии)
- **Рефактор = поверхность регрессий**: перенос фраз/inline в реестр и рендер промпта
  из БД — «1:1 по замыслу», а не безопасная замена; ловим тестами, катим по одному когу.
- **Превью нет** → редактор итерирует на тест-сервере (hot-reload мгновенный). Приемлемо.
- **Отката из БД нет** → страхуемся экспортом JSON перед крупной правкой.
- **Протаскивание `guild_id`**: раз в каталог идут ВСЕ строки, `persona.text(gid, …)`
  нужен и там, где gid сейчас не проброшен (форматтеры, часть эмбедов, глобальный
  error-handler, DM). Плюсы: почти все user-facing строки рождаются в контексте гильдии;
  где контекста нет — фолбэк на дефолт-персону (реестр). Это заметная, но механическая
  сантехника — закладываем в P4.
- **Объём ~300 строк**: P4 — самая долгая фаза; строго по когам с чекпоинтами.
- **Гвард** обязателен, иначе каталог протухнет (см. §6).
- **Инъекции**: промпт — доверенный ввод оператора; сообщения юзеров — данные (как сейчас).

## 14. Бэклог «по спросу» (максимум-версия, если упрётся)
Вводить **по одной оси, когда реально понадобится**, а не заранее:
1. **Полное владение профилем** (аватар/ник/баннер в персоне; смена персоны = смена
   лица) — если понадобится «лицо вместе с персоной».
2. **Слэш-команды** (описания; имена — с осторожностью) + ре-синк дерева команд Discord.
3. **Наследование** (persona.parent) — если появится много близких персон.
4. **Версии/откат в БД** + diff (сейчас роль бэкапа играет экспорт JSON).
5. **Превью-генерация** через мост (если тест-сервера мало).
6. **Per-guild override** персоны/строк; **мультиязычность** (locale поверх ключей);
   **AI-модель/temperature на персону**.

(Общий каталог всех user-facing строк — уже в основном объёме, P4: голос пронизывает
inline-строки типа «Добавила:», поэтому это требование, а не бэклог.)

## 15. Что я изменил против максимум-версии (v3) и почему
- **Наследование → «дублировать».** Наследование ломало семантику версий (откат не
  вернул бы вид, т.к. родитель уехал) и грозило бессвязным промптом при частичном
  override. Для 2–4 заказчиков дубликат проще и безопаснее. → §14.4.
- **Промпт цельный, без нарезки на секции.** Секции нужны были только под наследование;
  без него монолит проще и не рискует качеством (промпт чувствителен к порядку слов).
- **Общий каталог всех строк — ОСТАВЛЕН в основном объёме (P4), НЕ в бэклоге.**
  Поправка: я сначала ошибочно счёл inline-строки типа «Добавила:» нейтральными и убрал
  их. Но «Добавил**а**» — это род/голос персоны (для мужского → «Закинул»), значит их
  правка = само требование. Поэтому весь user-facing текст остаётся редактируемым.
  Упрощение: всё персона-скоупное, дефолты в реестре — без деления global/persona.
  В бэклог ушли только **слэш-команды** (внешняя зависимость от Discord). → §14.2.
- **Версии/откат и превью → в бэклог.** Версии плохо дружат с любым наследованием;
  превью через мост даёт один сэмпл на «примерных переменных» и вводит в заблуждение.
  Их роль в v1 играют экспорт JSON + мгновенный hot-reload на тест-сервере. → §14.5–6.
- **Профиль (аватар/ник) не трогаем в v1.** Убирает конфликт двух источников правды с
  существующим `bot_profile`; персона несёт только мягкую личность. → §14.1.
- **Per-guild override убран.** При «только оператор» и малом числе серверов проще
  сделать отдельную персону, чем городить второй уровень резолва. → §14.7.
- **«Каркас↔подача» — прагматично, не по каждой фразе.** Жёсткий формат-хвост система
  добавляет к AI-инструкциям; не режем догматично весь текст на два.
- **Оставил как было:** именованные библиотеки, AI-движок + фразы-fallback, режим на
  блок (дёшево и полезно), мягкая личность, роль оператора, экспорт/импорт, hot-reload,
  find-replace, границы (правила/числа — в `guild_settings`), «голос»=стиль, не TTS.

Итог: **~4 фазы вместо 10**, 3 таблицы вместо 6+, и основной запрос закрыт уже к P2–P3.
Максимум-версия не потеряна — она в §14, включается по мере реального спроса.
