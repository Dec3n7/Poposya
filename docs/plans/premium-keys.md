# Монетизация: активация Premium/Pro по ключам — ПЛАН

> Статус: **план, не реализовано.** Дизайн под реализацию. Опирается на готовый
> `EntitlementService` / `guild_entitlements` (см. `monetization-prep.md`).
>
> Идея: продавать Premium/Pro как **лицензионные ключи** фиксированных
> длительностей **30 / 90 / 180 / 365 дней** (SKU, §1a). Провайдер оплаты (Boosty
> на старте) выдаёт покупателю ключ; админ сервера активирует его
> `/premium activate key:<...>`. Ключ **самоподписан** (проверяется офлайн), а БД
> хранит потраченные ситы (`key_seats`) и payload выпущенного для инвентаря/
> экспорта (`premium_keys_issued`, вариант B — §2).

## 0. Два решения в основе

**A. Ключи, а не роли/вебхуки.** Provider-agnostic (Boosty → позже Stripe/крипта
без переделки), совпадает с моделью «Premium на сервер», идемпотентно (§27
аудита) без вебхуков.

**B. Ключи ПОДПИСАННЫЕ, а не пул в БД.** Ключ сам доказывает подлинность (HMAC);
БД помнит только потраченное. Плюсы против пула:
- нет пред-генерации и таблицы пула — ключ выпускается мгновенно из секрета
  (панель / CLI / будущий вебхук);
- проверка **офлайн, без БД** — брутфорсу нечего щупать, подделать 96-бит подпись
  нельзя;
- tier/срок/ситы **под подписью** — не подменить;
- отзыв целой партии — **ротацией секрета**;
- будущий Stripe: вебхук просто **выпускает подписанный ключ** на оплату.

## 1. Формат ключа (самоподписанный)

```
POPO-<base32(payload)>-<hmac[:12]>
payload = version · tier · seats · duration_days · key_expiry(дни от эпохи) · batch_id · nonce(64b)
hmac    = HMAC-SHA256(KEY_SIGNING_SECRET, payload)[:12]   # ~96 бит — не подделать
```

- `tier` ∈ {premium, pro}; `seats` = сколько серверов покрывает (premium=1, pro=5);
- `duration_days` ∈ {30, 90, 180, 365} — фиксированные SKU (см. §1a); mint любую
  другую длительность отклоняет. Значение под подписью — редемпшн берёт его из
  payload, не с клиента;
- `nonce` — уникальность (одноразовость на сит);
- `key_expiry` — срок годности САМОГО ключа (не выкупили за N дней → мёртв),
  проверяется офлайн, без cron;
- `batch_id` — партия ключа (под подписью → не подделать). Единица **отзыва**:
  пометил партию мёртвой → все её невыкупленные ключи больше не активируются
  (§3a). Компактен (напр. 24 бита — 16M партий);
- контрольная строка формата ловит опечатку до всего остального.

Секрет `KEY_SIGNING_SECRET` — только в окружении (как `web_session_secret`).
Два уровня отзыва: **точечный** — по `batch_id`, одна партия (§3a); **тотальный** —
ротация секрета, все невыкупленные ключи разом (крайняя мера).

## 1a. Длительности и пул генерации (SKU 30/90/180/365)

Ключи выпускаются **фиксированными длительностями** — SKU под товары Boosty, а не
произвольные дни. Константа `KEY_DURATIONS = (30, 90, 180, 365)`.

| `duration_days` | Ярлык | Premium — ориентир | Pro — ориентир |
|---:|---|---|---|
| 30  | Месяц   | 499 ₽ / $8.99        | 1 990 ₽ / $29 |
| 90  | Квартал | ~1 299 ₽ / $23 (−13%) | ~4 990 ₽ / $75 |
| 180 | Полгода | ~2 490 ₽ / $44 (−17%) | ~9 490 ₽ / $145 |
| 365 | Год     | 4 990 ₽ / $79 (−26%)  | 19 990 ₽ / $249 |

> Якоря 30/365 — из `MONETIZATION_IDEAS.md` §4. 90/180 — интерполяция со скидкой за
> длину; **подтвердить перед выкладкой**, здесь только для карты SKU.

- **SKU = (tier × duration)** → 8 товаров: `premium-30/90/180/365`,
  `pro-30/90/180/365`. `seats` привязан к tier (premium=1, pro=5), от длительности
  не зависит.
- `duration_days` **под подписью** — редемпшн доверяет payload, не клиенту; mint
  вне множества `KEY_DURATIONS` отклоняет (нет 45-дневных «на глаз»).
- **key_expiry ≠ duration.** `duration` — срок Premium ПОСЛЕ активации; `key_expiry`
  — срок годности невыкупленного ключа на полке. Держим `key_expiry` щедрым
  (напр. 730 дней), чтобы непроданный запас 30-дневок не умирал раньше времени.

### Пул как инвентарь по SKU

«Пул» = невыкупленные выпущенные ключи, сгруппированные по SKU. Считается из партий
`premium_key_batches` ⋈ `premium_keys_issued` ⋈ `key_seats` (§2); SKU = группировка
партий по (tier, duration), отозванные (§3a) считаем отдельно:

```
SKU            выпущено  выкуплено  остаток
premium-30        100        37        63
premium-365        50         8        42
pro-90            20         3        17
```

- **остаток** = `nonce`'ы этого SKU, ещё не потраченные полностью в `key_seats`;
- видно, какой SKU кончается → domint нужное количество той же партией (`batch`);
- длительности **стакаются** при редемпшне: купил 30, затем 365 на том же сервере
  → `expires = max(now, current) + timedelta(days=duration)` (§6), итого +395 дней.

### Генерация партии по SKU

CLI (быстрее всего «выложить»):

```bash
python -m scripts.mint --tier premium --duration 90 --count 100 --batch boosty-2026q3 > premium-90.txt
```

`--duration` ограничен `KEY_DURATIONS`; ключи в stdout (→ файл для пула товара
Boosty), payload'ы — в реестр. В панели `duration` — выпадающий список из четырёх
значений; tier + duration + count + batch → таблица партии → **Export CSV**.

## 2. Данные (миграция `0043`)

### `key_seats` — потраченные ситы (однократность + мультисервер)
| поле | тип | смысл |
|---|---|---|
| `nonce` | `String` | из ключа; общий для всех ситов одной лицензии |
| `guild_id` | `BigInteger` | сервер, на котором активировали сит |
| `tier` | `String(16)` | зафиксированный tier ключа |
| `redeemed_by_user` | `BigInteger` | кто активировал |
| `redeemed_at` | `DateTime` | когда |
| **UNIQUE** | | `(nonce, guild_id)` — один сервер нельзя занять дважды одним ключом |

### `premium_key_batches` — партии (пул-единица + отзыв)

Один mint-прогон = одна партия. Общие для всех её ключей поля живут здесь (не
дублируются в каждом ключе), плюс поля отзыва.

| поле | тип | смысл |
|---|---|---|
| `batch_id` | `Integer` PK | компактный id, идёт в payload ключа (§1) |
| `label` | `String` | человекочитаемая метка («boosty-2026q3») |
| `tier` | `String(16)` | premium / pro |
| `seats` | `Integer` | из SKU (premium=1, pro=5) |
| `duration_days` | `Integer` | 30 / 90 / 180 / 365 (SKU, §1a) |
| `key_expiry` | `Integer` | срок годности ключей партии на полке (дни от эпохи) |
| `count` | `Integer` | сколько ключей выпущено |
| `created_by` | `BigInteger` | оператор |
| `created_at` | `DateTime` | когда |
| `note` | `String` nullable | кому/куда (необяз.) |
| `revoked_at` | `DateTime` nullable | NULL = активна; иначе партия отозвана (§3a) |
| `revoked_by` | `BigInteger` nullable | кто отозвал |
| `revoke_reason` | `String` nullable | почему |

### `premium_keys_issued` — выпущенные ключи (реестр, вариант B)

| поле | тип | смысл |
|---|---|---|
| `nonce` | `String` PK | из payload; связь с `key_seats` |
| `batch_id` | `Integer` FK → `premium_key_batches` | партия ключа |

На ключ — только `nonce` + `batch_id`; tier/seats/duration/expiry берутся из партии.
Хранится **только payload** (ни подписи, ни секрета): полный ключ перевыпускается
детерминированно `mint(batch, nonce)` **лишь с env-секретом** — одна БД валидный ключ
не породит. Это **не** отвергнутый в §0 «пул валидных ключей», а инвентарь продавца:
пакетный экспорт, повторная выгрузка, статус, пул по SKU (§1a), отзыв партии (§3a).

Идём вариантом **B**: без реестра ни «пул по SKU», ни точечный отзыв не собрать. Пул
*валидных* ключей по-прежнему НЕ хранится — только потраченное (`key_seats`), партии
и payload выпущенного.

### `premium_key_attempts` — журнал попыток (rate-limit + видимость перебора)
| поле | тип |
|---|---|
| `id` PK / `user_id` / `guild_id` / `at` / `outcome` (`ok`/`invalid`/`used`/`full`/`rate_limited`) |
Индекс `(user_id, at)` — окно rate-limit.

## 3. Однократность + мультисит (Premium=1, Pro=5)

Семантика: ключ активируется **один раз на сервер**, и суммарно не больше `seats`
серверов. Premium (`seats=1`) ведёт себя как простой одноразовый ключ; Pro
(`seats=5`) — одна лицензия на 5 серверов (покупатель активирует один и тот же
ключ на своих 5 серверах, каждый раз ест сит).

Логика редемпшена (в одной транзакции, с блокировкой строк лицензии):
1. Проверить HMAC + `key_expiry` — **офлайн**. Не сошлось → «неверный ключ»
   (в БД не ходили).
2. **Партия отозвана?** `batch_id` из payload → `premium_key_batches.revoked_at`.
   Не NULL → «ключ отозван» (§3a). Проверка в БД, но это часть онлайн-редемпшна —
   офлайн-верификация подписи (шаг 1) остаётся без БД.
3. `SELECT guild_id FROM key_seats WHERE nonce=? FOR UPDATE` (лочим лицензию).
4. Разбор:
   - `guild_id` уже среди занятых → **продление** этого сервера (extend, §6), сит
     не тратится;
   - иначе если `занятых < seats` → **INSERT (nonce, guild_id)** + `grant(guild,
     tier, +duration)`;
   - иначе → «все N слотов этого ключа заняты» (показать сколько/какие).
5. Коммит. Либо и сит занят, и Premium выдан, либо ничего (откат).

`FOR UPDATE` на строках лицензии убирает гонку «два параллельных активатора
превысили seats». Уникальный `(nonce, guild_id)` не даёт занять сервер дважды.

**Освобождение сита:** оператор (и/или владелец в панели) может «снять сервер с
лицензии» — удалить `(nonce, guild)` + `revoke(guild)`; сит освобождается.

## 3a. Отзыв партии

Ситуации: партия утекла, реселлер ушёл в минус, промо закрыто, ошиблись в
длительности при выпуске. Отзыв **точечный** — по `batch_id` (одна партия), без
ротации секрета (та жжёт весь невыкупленный запас — крайняя мера, см. §1).

**Механика.** `batch_id` под подписью (§1). Отзыв = `UPDATE premium_key_batches SET
revoked_at=now, revoked_by, revoke_reason WHERE batch_id=?`. Редемпшн (§3, шаг 2) на
каждый ключ сверяет `revoked_at` — не NULL → «ключ отозван». Подделать `batch_id`
нельзя (подпись), а проверка живёт в уже-онлайн редемпшне, так что офлайн-
верификация подписи не страдает.

**Два режима:**
- **Soft (по умолчанию):** блокирует только БУДУЩИЕ активации невыкупленных ключей.
  Уже активированные серверы досиживают выданный срок — их Premium не трогаем.
- **Hard (по требованию):** плюс снять уже выданное. Трассируем `batch_id → nonces`
  (`premium_keys_issued`) `→ guild_id` (`key_seats`) и по каждому
  `EntitlementService.revoke(guild)` + аудит. Для утёкшей/ошибочной партии.

**Восстановление:** soft-отзыв обратим — `revoked_at=NULL` реактивирует партию.
Hard гранты назад не возвращает (выдать заново — новый ключ).

**Панель/CLI:** во вкладке инвентаря у партии кнопка «Отозвать» (оператор,
`require_operator`, reason обязателен) с выбором soft/hard; в аудит —
`entitlement.batch_revoke` (batch_id, режим, сколько серверов задето). CLI:
`python -m scripts.revoke_batch --batch-id 42 [--hard] --reason "leak"`.

**Гонок нет:** отзыв и редемпшн сериализуются на строке партии — активация ключа
отзываемой партии в момент отзыва либо успела до `revoked_at`, либо получила отказ.
Идемпотентно: повторный отзыв уже отозванной партии — no-op.

## 4. Rate-limit: 2 активации в час (анти-брутфорс)

- Ключ окна — `user_id`, окно 1 час скользящее, **порог 2**.
- Считаются **все** попытки (успех и провал) — иначе перебор обходил бы лимит.
- Хранилище — **БД** (`premium_key_attempts`), переживает рестарт бота (память
  сбрасывалась бы рестартом).
- Порядок: посчитать попытки за час → `>=2` → отказ **до** касания ключа + запись
  `rate_limited` → иначе запись попытки → редемпшн (§3).
- Двойная защита: неверная подпись отсекается ещё до БД (§1), а порог 2/час — вторым
  рубежом. Константа настраиваемая (`premium_key_attempts_per_hour: int = 2`);
  альтернатива «считать только провалы» описана как опция (чтобы легитимные
  активации не упирались в лимит).

## 5. Безопасность

- Ключ = одноразовый токен доступа, `nonce` из `secrets` (≥64 бит), подпись
  HMAC-256[:12] (~96 бит). Сравнение подписи — `hmac.compare_digest`.
- Единая ошибка на «нет ключа»/«занят»/«просрочен формат» там, где это не мешает
  UX — не помогаем перебору.
- Ответ команды — **`ephemeral`** (ключ и результат не в канал). Аргументы
  слэш-команды другим и так не видны, но ephemeral обязателен.
- Гейт активации — админ сервера (`Manage Guild`). Генерация ключей — оператор
  (`require_operator`).
- Аудит: генерация (`entitlement.keys_generate`) и активация
  (`entitlement.key_redeem`) — через `record_audit`.

## 6. Продление

Повторная активация того же ключа на **том же** сервере (или новый ключ на нём):
срок продлевается, не затирается:
```python
new_expires = max(now, current_expires or now) + timedelta(days=duration_days)
```

## 7. Панель: история активаций (кто / где / когда)

**Вкладка «Активации ключей» (оператор, `require_operator`).** Таблица журнала:

| Кто | Сервер | Когда | Tier | Ключ | Статус |
|---|---|---|---|---|---|
| `username` (id) | имя сервера + `guild_id` | дата-время | premium/pro | `…XXXX` (маскирован) | ok / used / full / rate_limited |

- Источник: `key_seats` (успешные активации: кто, сервер, когда, tier) +
  `premium_key_attempts` (все попытки, включая отказы — видно перебор/абузы).
- Имя сервера резолвим через `bot_guilds`/Discord (как в остальной панели); id
  показываем всегда (сервер мог стать недоступен).
- Ключ **маскируем** (последние 4 символа) — журнал не должен светить рабочие
  ключи целиком.
- Фильтры: по серверу, по пользователю, по статусу, по периоду. Пагинация.
- API: `GET /api/admin/premium-keys/activations` (оператор, page/limit/filters).

**На вкладке «Подписка» конкретного сервера** (админ сервера видит свой сервер):
строка «Активировано: `username` · `дата` · ключ `…XXXX` · до `expires_at`». Данные
из `key_seats` по этому `guild_id`. Так владелец видит, кто и когда включил Premium
на его сервере (спор/передача прав).

## 8. Доставка ключа с Boosty (вне кода)

Официального API у Boosty нет → авто-выдачу уникального ключа Boosty сам не делает.
Варианты:
1. **Полу-ручной (старт):** оператор генерит ключ в панели → отправляет покупателю
   после подписки. Для первых подписчиков ок.
2. **Boosty «товары» с уникальной выдачей** — если поддерживается (проверить в
   кабинете): покупка отдаёт код из пула автоматически.
3. **Длинные SKU против churn:** продавать ключи на 1/3/6/12 мес — доставка реже.
4. **Будущее (Stripe/крипта):** вебхук на оплату **выпускает подписанный ключ** сам,
   тогда же реализуется billing-идемпотентность §27. Редемпшн не меняется.

Генерация + активация (ценная механика) автоматизированы полностью уже на шаге 1.

## 10. Открытые вопросы

- **Pro=5**: подтвердить число ситов (сейчас из `MONETIZATION_IDEAS.md` — 5) и
  нужен ли Business с бóльшим числом. Заложено параметром `seats` в ключе.
- **Boosty-доставка** (§8): проверить авто-выдачу товара из пула.
- **Хэшировать ли nonce в `key_seats`** — не обязательно (nonce не секрет сам по
