# ADR-005 — `requirements.lock` — источник истины для деплоя

- **Статус:** Accepted (2026-08)
- **Связано:** план-первоисточник — [Poposya_improvement_plan §4](../plans/Poposya_improvement_plan.md)

## Контекст

В репозитории одновременно живут `pyproject.toml`, `requirements.txt` и
`requirements.lock`. Метаданные исторически рассинхронизированы с прод-локом, и
новому разработчику не очевидно: **где определены реальные production-зависимости?**
Неоднозначность приводит к «работает у меня, падает в проде» и к дрейфу версий.

## Решение

Явное разделение ролей:

```text
pyproject.toml     = метаданные проекта + конфигурация инструментов (ruff, mypy, pytest)
requirements.lock  = единственный источник истины для деплоя (хешированный, воспроизводимый)
requirements.txt   = верхнеуровневые прямые зависимости, из которых генерируется lock
```

Прод и образы собираются **только из `requirements.lock`** (dependency hash
locking сохраняется). Если `requirements.txt` и lock обязаны оставаться
согласованными — это проверяется автоматически (CI-гейт), а не на глаз.

## Последствия

- **Плюсы:** один ответ на вопрос «что реально ставится в прод»; воспроизводимые
  сборки; меньше дрейфа версий.
- **Минусы / цена:** дисциплина регенерации lock при смене зависимостей; нужен
  CI-шаг синхронизации.
- **Риски / что осталось открытым:** до внедрения авто-проверки рассинхрон
  возможен; при желании — свести к одному механизму (uv/poetry) в будущем ADR.
