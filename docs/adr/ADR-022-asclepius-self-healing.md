# ADR-022 (ASCLÉPIUS) — Самовосстанавливающаяся архитектура Poposya + WARDEN

- **Статус:** Proposed (2026-10-21) — **черновик**, не действует
- **Связано:** [ADR-004](ADR-004-warden-independent.md) (WARDEN — независимый деплой), [ADR-013](ADR-013-warden-docker-socket-allowlist.md) (socket-proxy), [ADR-010](ADR-010-panel-bot-listen-notify.md)/[ADR-011](ADR-011-durable-command-bridge.md) (мост, single-active), [ADR-018](ADR-018-health-schema-versioning.md) (health-контракт); спецификация WARDEN — `WARDEN/DESIGN.md`; деплой — [../DEPLOY.md](../DEPLOY.md); план — [scale-300-guilds](../plans/scale-300-guilds.md)

> Кодовое имя **ASCLÉPIUS** — Асклепий, бог врачевания: метафора
> «диагностировать → лечить → проверять → изолировать, а не латать вслепую».
>
> Это **черновик уровня Proposed**. Его цель сейчас — зафиксировать направление
> на будущее (релиз/хостинг), а не запустить немедленную реализацию. Часть
> пунктов при принятии, вероятно, распадётся на отдельные ADR (см. «Последствия»).

## Контекст

Сейчас — **самохостинг на одном сервере**, Docker Compose, WARDEN в отдельном
compose-проекте за socket-proxy, PostgreSQL в отдельном volume, off-box бэкап
дампами. WARDEN уже содержит: четыре цели наблюдения, двухуровневый health
score, дебаунс/гистерезис рестартов, внутренний watchdog (`os._exit(1)`),
граф зависимостей с подавлением каскада и персистентное состояние в томе
`data/` (`WARDEN/DESIGN.md`). CI проходит существующие проверки.

Сегодня отказ лечится вручную: обновление — `git pull && docker compose up -d
--build`, откат — `git checkout <commit> && up --build`, обход недоступного
apt — временным Dockerfile поверх образа, восстановление БД — из дампа по
RUNBOOK §3. Это работает, но не детерминировано и не аудируется.

При выходе в релиз/хостинг нужен слой, реагирующий на случайную порчу файлов,
неудачные обновления, аварии процессов и подозрительные изменения — **без**
переписывания Poposya и WARDEN. Ниже — предлагаемая архитектура.

**Основной принцип:** обнаружить изменение → проверить источник восстановления
→ выполнить только разрешённое действие → проверить результат → при неудаче
перейти в безопасное состояние.

Не следует автоматически заменять любой изменённый файл: код, конфигурация,
секреты и пользовательские данные требуют **разных** политик.

## Решение (предлагаемое)

Подход **immutable application + integrity monitoring + controlled recovery**:

1. Код поставляется в проверенных Docker-образах, закреплённых по digest.
2. CI формирует манифест релиза, provenance и подпись артефактов.
3. **Integrity Guard** обнаруживает изменения, но не изменяет файлы, эталоны
   или Docker-ресурсы.
4. WARDEN управляет восстановлением через явную state machine и **устойчивые**
   recovery budgets.
5. Docker socket-proxy пропускает минимальный набор API-операций.
6. Recovery policy разрешает действия только для фиксированных сервисов и
   доверенных релизов.
7. Данные восстанавливаются отдельными процедурами, не смешанными с
   восстановлением кода.
8. После каждого действия — health checks и smoke tests. Неудача → ограниченный
   rollback или изоляция, но **не** бесконечный цикл рестартов.

На первом этапе Integrity Guard может быть модулем WARDEN или небольшим
read-only сервисом. Новую БД или брокер сообщений вводить не обязательно.

### Логическая схема

```text
CI / доверенный источник релизов
  ├─ тесты, SBOM, provenance
  ├─ immutable Docker images
  ├─ image digests и подписи
  └─ integrity manifest
           |
           v
Release Store (текущий + предыдущий релиз, манифесты, метаданные)
           |
           v
Integrity Guard ───── Health Monitor
           |                    |
           +---------+----------+
                     v
          WARDEN Recovery Controller
          ├─ классификация инцидента
          ├─ state machine и recovery budgets
          ├─ сериализация операций
          └─ аудит
                     v
             Docker socket proxy
                     v
               Docker Engine (Poposya · WARDEN · PostgreSQL · volumes)

Внешнее доверенное хранилище: бэкапы PostgreSQL, проверенные релизы,
копии, защищённые от перезаписи с основного сервера.
```

Это логическая схема, а не требование создавать каждый блок контейнером. Она
ложится поверх существующей топологии WARDEN (`WARDEN/DESIGN.md`).

### Ответственность и границы

| Компонент | Разрешено | Запрещено |
|---|---|---|
| Poposya | прикладные функции, работа с собственными данными | управлять Docker, менять эталон целостности или recovery policy |
| Integrity Guard | читать проверяемые файлы, проверять digest/подписи, публиковать события | изменять файлы, перезаписывать манифест, запускать контейнеры |
| Health Monitor | проверять readiness, БД и ключевые функции | самостоятельно запускать параллельные recovery actions |
| WARDEN | классифицировать события, управлять state machine и разрешёнными действиями | произвольный shell, `exec` в контейнере, редактирование эталонов |
| Docker socket proxy | минимальные необходимые API-методы | универсальный доступ к Docker API |
| Release Store | хранить доверенные образы, подписи, манифесты | принимать эталоны от запущенных приложений |
| PostgreSQL/volumes | хранить данные | заменяться/удаляться в процессе восстановления кода |

**Docker socket-proxy** ограничивает API-методы, но не обязательно обеспечивает
политику «только контейнер X». Нужны два уровня: (1) proxy блокирует ненужные
категории (`exec`, build, произвольные сети/volumes); (2) WARDEN разрешает
операции только для фиксированных логических сервисов и проверенных digest. При
необходимости более строгой границы — небольшой recovery-broker с типизированными
действиями (`RESTART_POPOSYA`, `ROLLBACK_WARDEN`), без произвольных Docker-параметров.
Не монтировать Docker socket в Poposya или Integrity Guard. Это **уточнение
ADR-013**, а не новое решение.

### Сохранение существующей архитектуры

- Poposya сохраняет доменные слои, API, Discord-логику и контракты с БД.
- WARDEN сохраняет health score, decision engine, watchdog, budgets, журнал.
- Состояние recovery episode — в существующем томе состояния WARDEN.
- PostgreSQL остаётся хранилищем данных Poposya.
- Новые компоненты вводятся постепенно; Kubernetes и новый брокер не нужны.

Контейнерное разделение **не защищает** от администратора или полной
компрометации хоста, где работают все компоненты (см. §«Реакция на взлом»).

## Категории файлов и политика восстановления

| Категория | Примеры | Политика |
|---|---|---|
| Неизменяемый код | Python-модули, frontend build, зависимости | пересоздать контейнер из доверенного образа |
| Deployment-конфигурация | Compose-файлы, overrides, deployment policy | остановить deploy и проверить доверенную версию |
| Конфигурация приложения | defaults, настройки, feature flags | проверять допустимость изменения и его источник |
| Секреты | Discord tokens, ключи, пароли | не копировать вслепую; при подозрении — отозвать и заменить |
| Данные | PostgreSQL, пользовательские файлы | специализированное восстановление из согласованного бэкапа |
| Временные данные | кэш, пересоздаваемые артефакты | пересоздать, если явно разрешено |

Для кода предпочтительно **пересоздание контейнера** из доверенного образа, а не
копирование файлов поверх работающего приложения. Read-only rootfs включать
поэтапно, предварительно проверив пути записи (логи, временные файлы, кэш,
генерируемые артефакты).

## Integrity manifest

Манифест связывает версию приложения с конкретными образами и
deployment-конфигурацией. Концептуальный JSON (digests — placeholders):

```json
{
  "schema_version": 1,
  "release_id": "poposya-YYYY.MM.DD.N",
  "source_commit": "REPLACE_WITH_COMMIT",
  "artifacts": {
    "poposya": { "image": "registry.example.com/poposya", "digest": "sha256:REPLACE" },
    "warden":  { "image": "registry.example.com/warden",  "digest": "sha256:REPLACE" }
  },
  "deployment": { "compose_config_digest": "sha256:REPLACE", "policy_version": 1 },
  "health_profile": {
    "require_readiness": true,
    "require_database_connectivity": true,
    "require_smoke_tests": true
  }
}
```

Требования: манифест генерирует CI из реально собранных артефактов; подпись
проверяется на сервере, приватный ключ на production-хосте не хранится; формат
имеет однозначную канонизацию; проверяются подпись, digest и provenance **до**
запуска; Poposya и обычный процесс WARDEN не могут менять эталон; предыдущий
проверенный релиз хранится до конца окна наблюдения; Release Store по
возможности вне основного сервера.

Для файлового манифеста хранится относительный путь, тип, SHA-256, ожидаемые
метаданные, допустимое действие. Пути валидируются относительно фиксированного
корня (path traversal, симлинки, владельцы, права). Произвольные пути из события
не принимаются.

## Recovery state machine

```text
MONITORING → SUSPECTED → VALIDATING → CLASSIFIED → RECOVERING → VERIFYING
                                                       │
                                        success ───────┴──→ HEALTHY → MONITORING
                                        failure ──────────→ ROLLBACK
                                                              │
                                               success ───────┴──→ VERIFYING
                                               failure ──────────→ QUARANTINED
```

При недоверенном эталоне, признаках компрометации, исчерпании бюджета или
невозможности безопасно определить результат — переход в `QUARANTINED`.

Правила:

1. Дублирующиеся события объединяются в один episode.
2. До действия проверяются доверенность эталона, разрешённость операции, budget.
3. При подозрении на компрометацию нельзя просто заменить файл: сохранить
   данные инцидента, ограничить сервис, проверить артефакты, оценить ротацию
   секретов.
4. После Docker-операции фактическое состояние сверяется с ожидаемым.
5. `HEALTHY` — только после всех проверок и окна стабильности.
6. Не повторять вслепую потенциально разрушительную операцию при неизвестном
   результате предыдущей.

**Устойчивое хранение состояния.** Состояние episode не должно жить только в
памяти. В существующем хранилище WARDEN — таблица `recovery_episodes` с полями:
`episode_id`, `service`, `state`, `reason`, `release_before`, `release_target`,
`attempt_count`, `started_at`, `updated_at`, `last_action`, `last_error`,
`lease_owner`, `lease_expires_at`, `verification_result`. Перед операцией —
атомарно записать попытку и взять lease/lock на сервис. После рестарта WARDEN
сверяет запись, историю действий и фактическое состояние Docker. Бюджеты **не**
сбрасываются при рестарте.

## Recovery budgets

Начальные параметры для тестирования (сверить с текущими лимитами WARDEN):

- одна активная recovery episode на сервис;
- максимум две попытки автоматического восстановления в одном эпизоде;
- cooldown не менее пяти минут после исчерпания попыток;
- не более трёх рестартов одного сервиса за час;
- не более одного переключения релиза в одном эпизоде;
- никаких бесконечных повторов при недоступности Docker, БД или Release Store.

Лимиты переживают перезапуск WARDEN. Раздельно учитывать рестарты, пересоздания,
rollback и операции с данными. Успешное закрытие episode **не** обнуляет
почасовой бюджет. Это развитие уже существующих budgets WARDEN, а не новая
подсистема.

## Безопасный deploy и rollback

1. CI собирает образы, тесты, SBOM/provenance, подписанный манифест.
2. Сервер загружает артефакты, проверяет digest и подписи.
3. Предыдущий рабочий релиз сохраняется.
4. Новая версия поднимается в отдельном слоте (`poposya-blue`/`-green`).
5. Readiness checks, smoke tests, проверка подключения к БД.
6. Трафик переключается только после успешных проверок.
7. Предыдущая версия живёт до конца окна наблюдения.
8. Провал → возврат трафика к старой версии, новый экземпляр останавливается,
   событие фиксируется.

Нельзя допускать, чтобы две версии одновременно выполняли несовместимые
миграции или дублировали single-active worker/Discord-команды. Для миграций —
стратегия expand/contract и совместимость старого и нового кода со схемой БД.
Rollback кода не гарантирует обратимость миграции.

## Резервное копирование и восстановление данных

**PostgreSQL:** регулярные бэкапы; архивирование WAL при необходимости PITR;
минимум одна копия вне основного сервера с защитой от перезаписи; регулярное
тестовое восстановление в отдельный экземпляр; проверка целостности и
прикладных инвариантов; явные RPO/RTO.

**Состояние WARDEN:** корректное завершение записи; бэкап, совместимый с
режимом journal/WAL; тестирование восстановления; простое копирование открытого
файла не считать согласованным snapshot.

Восстановление кода **не** должно автоматически удалять, пересоздавать или
заменять volumes с данными.

## Fault-injection тесты

Выполнять в отдельном тестовом compose-стеке с отдельными БД и volumes.

| ID | Инъекция | Ожидаемый результат |
|---|---|---|
| FI-01 | аварийное завершение Poposya | WARDEN ограниченно перезапускает сервис |
| FI-02 | изменение кода в тестовом контейнере | mismatch обнаружен; контейнер пересоздан из доверенного digest |
| FI-03 | неверный хеш в манифесте | релиз/восстановление отклоняется |
| FI-04 | неверная подпись артефакта | недоверенный образ не запускается |
| FI-05 | новый релиз не проходит readiness | трафик не переключается или возвращается |
| FI-06 | WARDEN падает после фиксации попытки, до Docker-операции | после рестарта состояние сверяется, действие не дублируется вслепую |
| FI-07 | WARDEN падает после пересоздания контейнера | контроллер обнаруживает фактическое состояние и продолжает проверку |
| FI-08 | 20 одинаковых событий | одна episode, не более одной параллельной операции на сервис |
| FI-09 | proxy блокирует нужный API-вызов | ошибка фиксируется, бесконечных повторов нет |
| FI-10 | Docker Engine временно недоступен | ограниченные повторы с backoff, затем безопасный исход |
| FI-11 | PostgreSQL недоступен во время health check | приложение не объявляется здоровым; миграции не запускаются автоматически |
| FI-12 | несовместимая схема БД | переключение блокируется; отдельная процедура |
| FI-13 | повреждённый backup | проверка обнаруживает повреждение |
| FI-14 | изменён `compose.yaml` | deploy остановлен до проверки доверенной конфигурации |
| FI-15 | исчерпан recovery budget | сервис изолирован/остановлен по политике, создано уведомление |
| FI-16 | Release Store недоступен | не используется неизвестный источник, проверка подписи не отключается |
| FI-17 | неожиданно изменён секрет | секрет не копируется вслепую; предусмотрена ротация |
| FI-18 | сбой во время rollback | episode остаётся незавершённой; после рестарта сверяется фактическое состояние |

**Критерии прохождения:** данные PostgreSQL не удаляются при восстановлении
кода; нет двух одновременных recovery actions на сервис; budget переживает
рестарт WARDEN; неподписанные/неразрешённые образы не запускаются; после
восстановления выполняются проверки здоровья; при неустранимой ошибке — безопасное
состояние и уведомление; backup пригоден только после успешного тестового
восстановления.

## Наблюдаемость и аудит

Метрики в существующую наблюдаемость WARDEN: `integrity_mismatch_total`,
`recovery_attempts_total`, `recovery_success_total`, `recovery_failure_total`,
`recovery_duration_seconds`, `rollback_total`, `recovery_budget_exhausted_total`,
`artifact_signature_failure_total`, `backup_restore_test_last_success_timestamp`,
возраст последней проверенной резервной копии, состояние текущей episode и
причина последнего отказа.

Структурированные логи включают `episode_id`, сервис, `release_id`, причину,
действие, результат проверки и длительность. Токены, пароли, приватные ключи и
содержимое секретных конфигураций **не** записывать.

## Реакция на возможный взлом

Восстановление одного файла недостаточно, если злоумышленник мог менять код,
процессы, конфигурацию или секреты. При признаках компрометации: прекратить
автоматические действия, которые могут уничтожить доказательства; изолировать
затронутый сервис (насколько безопасно для данных); сохранить журналы и сведения
об инциденте; проверить доверенность образов, манифестов и
deployment-конфигурации; пересоздать контейнеры из доверенного источника после
оценки; отозвать и заменить секреты, которые могли быть раскрыты; проверить
целостность данных и доступность backup; при компрометации хоста восстановить
среду из внешнего доверенного источника.

**WARDEN нельзя считать доверенным, если злоумышленник контролирует тот же хост.
Контейнерное разделение само по себе эту проблему не решает.**

## Критерии готовности к production

Автоматическое восстановление кода можно включать, когда: CI выпускает
проверенные immutable-образы; манифест защищён от изменения приложением и
обычным процессом WARDEN; подписи и digest проверяются до запуска; контейнеры не
могут произвольно менять собственный код; Docker proxy ограничен методами, а
WARDEN — целями; recovery state и budgets переживают рестарт WARDEN; повторные
события не создают параллельные операции; rollback проверен на тестовом релизе;
PostgreSQL и состояние WARDEN восстанавливаются из backup в тестовой среде;
fault-injection сценарии имеют проверяемые результаты; есть отдельная процедура
восстановления после компрометации хоста.

## План внедрения (этапы)

1. **Инвентаризация** — сервисы Compose, образы, mounts, сети, переменные;
   текущие budgets и разрешённые Docker API-методы; health checks и критерии
   здорового состояния; модель угроз и политика для каждой категории данных.
2. **Hardening контейнеров** — закрепить образы по digest; убрать запись в rootfs
   где совместимо; непривилегированные пользователи; `cap_drop`,
   `no-new-privileges`, ограниченные writable volumes; проверить логи, tmp, кэш.
3. **Доверенные релизы** — манифест в CI; подпись и проверка на сервере; хранить
   предыдущую версию; защитить deployment-конфигурацию и recovery policy.
4. **State machine WARDEN** — устойчивое хранение episode; сериализация операций;
   idempotency, lease/lock, восстановление после рестарта; сначала разрешить
   restart и health verification.
5. **Integrity Guard — режим наблюдения** — сверять доверенные артефакты и
   критичные файлы; собирать события, оценивать ложные срабатывания; **не**
   включать авто-восстановление до проверки детектирования.
6. **Контролируемое восстановление кода** — пересоздание только из проверенных
   digest; budgets и cooldown; изоляция при подозрении на компрометацию; проверка
   результата каждой операции.
7. **Deploy, rollback и данные** — безопасное переключение версий; совместимость
   миграций; независимые бэкапы; автоматизировать тестовое восстановление
   PostgreSQL и состояния WARDEN.
8. **Fault injection и production readiness** — FI-01…FI-18 в pipeline или
   регулярный recovery suite; проверить уведомления и аудит; документировать
   ручной recovery path; авто-режим только для проверенных сценариев.

## Последствия

- **Плюсы:** меньше риска незаметного изменения исполняемого кода; неудачный
  релиз откатывается автоматически; восстановление предсказуемо и аудируемо;
  recovery loops ограничены устойчивыми бюджетами; данные отделены от жизненного
  цикла контейнеров; существующая архитектура Poposya и WARDEN сохраняется.
- **Минусы / цена:** работа над CI, подписанием артефактов и deployment-процессом;
  blue-green требует координации фоновых задач и Discord-интеграций; read-only
  rootfs потребует адаптации путей записи; подпись артефакта не гарантирует
  отсутствие уязвимостей; локальная система не спасёт при уничтожении хоста и всех
  локальных копий; авто-восстановление обязано останавливаться при неясной
  доверенности источника или состоянии данных.
- **Риски / что осталось открытым (для принятия):**
  - **Размер.** Это не одно решение, а минимум три (supply-chain/deploy ·
    recovery в WARDEN · backup/restore данных). При принятии — вероятно, разбить
    на отдельные ADR (следующие свободные номера), а этот оставить зонтичным.
  - **Blue-green для бота.** Discord Gateway — stateful single connection,
    голосовые сессии привязаны к процессу, мост панель↔бот (`LISTEN/NOTIFY`,
    ADR-010/011) — single-active. Для `bot` blue-green не тривиален; разумно
    ограничить его `api`/`web`, а `bot` обновлять stop→start с коротким окном.
  - **Гонка авто-миграций.** Сейчас миграции Alembic применяются при старте
    бота; при двух инстансах нужен advisory-lock / single-runner, иначе
    `upgrade` небезопасен. Конкретный блокер критериев готовности (FI-12).
  - **Read-only rootfs.** Пишут: `/app/data` (SQLite/логи/бэкапы/аудиокэш),
    генерируемые рендеры, `.pyc`. Также **противоречит** immutable-модели
    практика `COPY src/` поверх образа (обход недоступного apt при пересборке) —
    её придётся заменить сборкой по digest.
  - **Хранилище episode.** Для таблицы `recovery_episodes` закрепить
    WAL/`synchronous=FULL` — состояние обязано переживать `kill -9`.
  - **Модель угроз.** Явно ранжировать: (а) случайный сбой/неудачный деплой —
    дёшево; (б) порча файлов админом — средне; (в) компрометация хоста — эта
    архитектура и не обещает решения. От приоритета зависит, сколько этапов
    вообще оправдано на текущем этапе (самохостинг).
  - **Синхронизация с ADR-018.** health-контракт и его версия уже зафиксированы;
    любые изменения `health_profile` манифеста должны ссылаться на него.

## Итоговое решение (предлагаемое)

Внедрять самовосстановление постепенно, без переписывания существующих слоёв:
(1) immutable images и hardening; (2) доверенные подписанные релизы и
защищённый Release Store; (3) устойчивая recovery state machine внутри WARDEN;
(4) Integrity Guard в read-only; (5) авто-пересоздание и rollback для проверенных
сценариев; (6) отдельные процессы восстановления данных; (7) fault-injection и
мониторинг.

**Ключевое правило:** автоматизировать только действия, для которых известны
доверенный источник, допустимая область воздействия и способ проверить успех.
Если доверенность или целостность данных сомнительны — изолировать проблему и
уведомить оператора, а не исправлять всё вслепую.
