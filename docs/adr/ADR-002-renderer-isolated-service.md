# ADR-002 — Renderer вынесен в изолированный сервис

- **Статус:** Accepted (2026-07)
- **Связано:** [ADR-004](ADR-004-warden-independent.md), [ADR-007](ADR-007-hexagonal-dependency-rule.md)

## Контекст

Часть возможностей бота требует рендеринга изображений (карточки, визуализации).
Тяжёлый графический стек — headless-браузер / Chromium (~300–400 МБ), системные
шрифты, GPU-независимый растеризатор — не должен жить внутри процесса бота:

- он раздувает образ и память основного процесса;
- падение/зависание рендера не должно ронять event loop бота;
- у рендера свой цикл релиза и свои системные зависимости.

## Решение

**Рендеринг вынесен в отдельный сервис `renderer/`** с собственным образом. Бот
общается с ним через узкий HTTP-контракт (`RenderClient`), а не вызывает
графику in-process. Клиент замоканному серверу-заглушке не доверяет — тесты
(`tests/test_render_client.py`) поднимают настоящий aiohttp-сервер.

С точки зрения слоёв ([ADR-007](ADR-007-hexagonal-dependency-rule.md)) renderer —
инфраструктурная деталь за портом: домен и application знают только интерфейс
клиента, а не движок рендера.

## Последствия

- **Плюсы:** основной процесс лёгкий; отказ рендера изолирован и деградирует
  штатно; renderer обновляется независимо ([deployment isolation](ADR-006-feature-oriented-architecture.md)).
- **Минусы / цена:** ещё один сервис в `docker-compose` и в эксплуатации;
  сетевой хоп и таймауты вместо вызова функции.
- **Риски / что осталось открытым:** контракт «бот↔renderer» версионируется
  неявно; при расширении рендера (унификация карточек `/rank` на браузерный
  движок) стоит зафиксировать формат запроса.
