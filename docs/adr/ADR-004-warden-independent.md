# ADR-004 — WARDEN — независимый деплой, не часть приложения

- **Статус:** Accepted (2026-07)
- **Связано:** [ADR-013](ADR-013-warden-docker-socket-allowlist.md), спецификация — [WARDEN/DESIGN.md](../../../WARDEN/DESIGN.md), история — [../plans/WARDEN.md](../plans/WARDEN.md), [../plans/WARDEN V2.md](../plans/WARDEN%20V2.md)

## Контекст

Боту нужен внешний сторож: `restart: unless-stopped` ловит выход процесса, но не
зависание event loop, а сам бот не может достоверно перезапустить себя. Сторож,
живущий внутри приложения, разделил бы с ним судьбу — упавший процесс не
перезапустит сам себя.

## Решение

**WARDEN — отдельный сервис и отдельный деплой.** Он **не импортирует код
приложения**, наблюдает Poposya только снаружи — по HTTP-хелсчекам и Docker API —
и имеет собственный жизненный цикл, тесты и образ.

- Единственная зависимость — `aiohttp`; Docker API, Discord REST и Gateway
  реализованы напрямую (из Gateway нужны 4 опкода из 12), чтобы не тащить
  `discord.py`.
- Граница «Poposya ↔ WARDEN» — это health-контракт (`/health/full`,
  `/api/health`), а не общий код. Изменение health API не должно молча ломать
  автономное лечение — контракт стоит версионировать.
- WARDEN сознательно **простой**: `probe → measure → score → decision → action`.
  Бизнес-логику Poposya, сложную шину и plugin-фреймворки внутрь не добавляем.

## Последствия

- **Плюсы:** сторож переживает падение бота; независимый релиз и тесты (415
  проходящих); Decision Engine — чистая функция, объяснимая и предсказуемая.
- **Минусы / цена:** дублирование мелочей (свой Docker/Discord-клиент); связь
  через контракт, а не типы — нужны contract-тесты против формата health.
- **Риски / что осталось открытым:** привязка к именам контейнеров Compose
  (лучше перейти на Docker labels); версионирование health-схемы пока неявное.
