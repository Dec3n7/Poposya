# ADR-008 — Пер-серверные настройки через единый settings-provider

- **Статус:** Accepted (2026-07-11)
- **Связано:** [ADR-009](ADR-009-tier-enforcement-seam.md), [ADR-010](ADR-010-panel-bot-listen-notify.md), план-первоисточник — [guild_settings_plan](../plans/guild_settings_plan.md)

## Контекст

Бот обслуживает много серверов, и поведение фич (каналы, пороги модерации, роли,
параметры AI, лимиты музыки/находок/кино) должно настраиваться **отдельно для
каждой гильдии**. При этом секреты и инфраструктура (`discord_token`, `database_url`,
API-ключи, `backup_*`, `outbox_*`) — глобальны и настройке по серверам не
подлежат. Нужен единый способ читать «эффективное» значение настройки, чтобы
~88 мест чтения не расползлись в разные механизмы.

## Решение

Единая модель `GuildSettings` (pydantic-схема в `application/guild_config/schema.py`)
описывает **все** per-guild ключи, их типы, диапазоны и дефолты — и является
единственным источником правды: чего нет в модели, то нельзя переопределить в
принципе (граница фиксируется типом, а не документацией).

Все чтения сходятся в один порт — `ISettingsProvider.get(guild_id, key, default)`
(реализация `GuildSettingsService`): `_cfg(...)`, `gs.get(...)` и `flag_on(...)`
идут через него. UI (`/config`, вкладки «Настройки»/«Модули» панели) строится
поверх и бизнес-код не трогает. Секреты/инфра остаются в глобальном `Settings`
из `.env` и через провайдер не проходят.

## Последствия

- **Плюсы:** одна точка чтения настроек → на неё можно навесить сквозные
  поведения (кламп тарифа — [ADR-009](ADR-009-tier-enforcement-seam.md); инвалидация
  кэша — [ADR-010](ADR-010-panel-bot-listen-notify.md)) без правки 88 сайтов;
  чёткая граница «настройка vs секрет».
- **Минусы / цена:** атрибутный путь `resolved(gid).<field>` идёт мимо провайдера
  и сквозными обёртками не перехватывается — тарифные поля надо читать через `get`.
- **Риски / что осталось открытым:** коллизия имени `gs` (провайдер vs глобальный
  `Settings`) — механически трактовать любой `gs.<field>` как настройку нельзя.
