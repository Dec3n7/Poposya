# ADR-001 — PostgreSQL — производственная БД; SQLite только для локалки и тестов

- **Статус:** Accepted (2026-07-17 — Postgres live в проде)
- **Связано:** [ADR-010](ADR-010-panel-bot-listen-notify.md), [ADR-011](ADR-011-durable-command-bridge.md), план-первоисточник — [CONCURRENCY_PLAN](../plans/CONCURRENCY_PLAN.md)

## Контекст

Веб-панель ([ADR-012](ADR-012-web-panel-reuses-domain.md)) сделала систему
**двухпроцессной**: бот и API пишут в одну БД одновременно. Пока писатель один
(бот), паттерны read-modify-write и check-then-act безопасны по факту; со вторым
писателем это перестаёт быть правдой, и часть путей начинает **портить данные**
(потеря апдейта, затирание несвязанных полей в `RelationshipProfile.save`).

SQLite не даёт того, что для этого нужно в проде: строковых блокировок
(`SELECT … FOR UPDATE`), настоящей конкурентной записи и межпроцессной сигнализации
(`LISTEN/NOTIFY`). При этом SQLite бесценен для скорости: мгновенный локальный
запуск и быстрый прогон тестов без внешней службы.

## Решение

**Производственная БД — PostgreSQL.** Бизнес-инварианты под конкуренцией
обеспечиваются средствами Postgres: `SELECT … FOR UPDATE` на write-путях,
`INSERT … ON CONFLICT`, частичные уникальные индексы, `LISTEN/NOTIFY`.

**SQLite остаётся поддерживаемым бэкендом только для локальной разработки и
тестов.** Код пишется диалект-нейтрально: `with_for_update` и `ON CONFLICT` на
SQLite деградируют в no-op / нативную поддержку, а сам SQLite сериализует записи,
поэтому тесты остаются корректными. Тесты гонок гоняются **только на Postgres**
(SQLite их не воспроизводит — см. `tests/test_concurrency_postgres.py`).

## Последствия

- **Плюсы:** реальная защита от порчи данных под двумя писателями; готовность к
  панели; бесплатный `LISTEN/NOTIFY` как транспорт для настроек, персон,
  тарифов и командного моста — без Redis/брокера.
- **Минусы / цена:** двойная поддержка диалектов; часть багов конкуренции ловится
  только в Postgres-тестах, которым нужен живой Postgres в CI/локально.
- **Риски / что осталось открытым:** пути, обходящие `get_or_create` (фоновые
  list-запросы), требуют отдельного покрытия локами; backup считается надёжным
  только с restore-тестом (см. `tests/test_tech_debt.py`).
