# ADR-003 — Критичные доменные события — через event bus + transactional outbox

- **Статус:** Accepted (2026-07)
- **Связано:** [ADR-001](ADR-001-postgresql-production-database.md), [ADR-007](ADR-007-hexagonal-dependency-rule.md), тесты — `tests/test_tech_debt.py`

## Контекст

Модули общаются событиями, а не прямыми вызовами ([ADR-007](ADR-007-hexagonal-dependency-rule.md)):
`RelationshipRoleChanged`, `ExclusiveTransferred`, `FindClaimed` и т.п. Часть
событий **критична** — на них завязаны видимые пользователю эффекты (выдача роли,
переход титула). Наивная публикация «в памяти после коммита» теряет событие, если
процесс упал между `commit` и `publish`: строка в БД есть, эффект не случился, и
восстановить нечего.

## Решение

**Критичные доменные события пишутся в outbox в той же транзакции, что и
изменение данных**, а публикуются отдельным диспетчером.

- `UnitOfWork.add_event(...)` кладёт событие в таблицу `outbox` внутри бизнес-
  транзакции; коммит атомарно фиксирует и данные, и запись о событии.
- `OutboxDispatcher` доставляет неопубликованные записи в `IEventBus` и помечает
  `published_at`; повторный проход уже опубликованное не шлёт (at-least-once с
  идемпотентной пометкой).
- Регистрация события без строкового `event_type` падает **громко на импорте**
  (`_register`), чтобы критичное событие не потерялось под сентинелом.

Некритичные уведомления (integration actions) могут идти по шине напрямую — outbox
для них избыточен.

## Последствия

- **Плюсы:** критичное событие переживёт краш между commit и publish; чёткая
  граница «доменное событие» vs «integration action»; поведение покрыто тестами
  (roundtrip сериализации, доставка недоставленного, отказ регистрации без типа).
- **Минусы / цена:** доставка at-least-once — обработчики критичных событий
  должны быть идемпотентны; лишняя таблица и фоновый диспетчер.
- **Риски / что осталось открытым:** не превращать шину в «глобальную магию» —
  различать domain events и application actions осознанно.
