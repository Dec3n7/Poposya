# ADR-007 — Гексагональная модульная архитектура + Dependency Rule

- **Статус:** Accepted (2026-07) — фундаментальное решение проекта
- **Связано:** [ADR-003](ADR-003-event-bus-outbox.md), [ADR-006](ADR-006-feature-oriented-architecture.md), живые правила — [../ARCHITECTURE.md](../ARCHITECTURE.md), [../AI_RULES.md](../AI_RULES.md), исходное ТЗ — [../plans/TZ.md](../plans/TZ.md)

## Контекст

Проект должен жить годами и наращивать фичи без превращения в «большой ком грязи».
Discord API, СУБД, внешние сервисы меняются; бизнес-логика не должна зависеть от
их деталей. Нужна структура, в которой добавление модуля не требует понимать весь
проект, а инфраструктуру можно заменить без правки домена.

## Решение

**Гексагональная (ports & adapters) модульная архитектура с одним направлением
зависимостей.** Четыре слоя и жёсткое правило:

```text
Presentation → Application → Domain ← Infrastructure
```

- **Domain** ничего не знает о Discord, SQLAlchemy, HTTP, DI — только сущности,
  value objects, доменные события и интерфейсы репозиториев.
- **Application** знает Domain и интерфейсы, но не их реализации; каждое действие
  пользователя — отдельный тонкий `UseCase`.
- **Infrastructure** зависит от Domain (реализует порты); SQLAlchemy живёт
  **только** здесь.
- **Presentation** (Discord-коги, slash, views) — максимально тонкий: получил
  данные → вызвал use case → ответил. Бизнес-логики в коге нет.

Связь между фичами — только через события ([ADR-003](ADR-003-event-bus-outbox.md)),
не прямыми вызовами. Абстракцию заводим только при ≥2 использованиях/реализациях,
а не «на будущее». Живой чек-лист правил — в [ARCHITECTURE.md](../ARCHITECTURE.md)
и [AI_RULES.md](../AI_RULES.md).

Контрольный вопрос перед PR: **«если удалить этот модуль целиком, сломаются ли
остальные?»** Если нет — граница верна.

## Последствия

- **Плюсы:** заменяемость инфраструктуры без правки домена; тестируемость use
  case'ов без Discord/БД; независимость модулей; единый предсказуемый стиль.
- **Минусы / цена:** больше файлов и церемонии (DTO, порты, use case'ы) даже для
  простых операций; дисциплина Dependency Rule требует ревью.
- **Риски / что осталось открытым:** технически-слоевую раскладку постепенно
  двигаем к feature-вертикалям ([ADR-006](ADR-006-feature-oriented-architecture.md));
  крупные объекты (`PersonaRegistry`) — кандидаты на разукрупнение.
