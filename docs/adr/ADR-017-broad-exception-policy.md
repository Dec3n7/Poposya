# ADR-017 — Broad exception: допустим на границе, где есть осознанная recovery

- **Статус:** Accepted (2026-10-21)
- **Связано:** план-первоисточник — [Poposya_improvement_plan §16](../plans/Poposya_improvement_plan.md); [ADR-016](ADR-016-unified-news-poller.md), [ADR-004](ADR-004-warden-independent.md), [ADR-007](ADR-007-hexagonal-dependency-rule.md)

## Контекст

`except Exception` встречается в `src/` ~101 раз. Это широкий перехват: он ловит
и ожидаемые operational-сбои (сеть, БД, внешний API), и **programming bugs**
(`AttributeError`, `TypeError`, ошибки логики), которые такой перехват прячет —
баг выглядит как «временный сбой», а не как дефект. Именно поэтому широкий
перехват — риск, требующий явной политики, а не запрета.

При этом часть `except Exception` **оправдана**: на границах, где мы осознанно
изолируем сбой одного шага, чтобы не уронить весь процесс (такт фонового цикла,
одна health-проверка из многих, публикация события в outbox). Уже есть и
централизованный счётчик ошибок (`ErrorRateCounter`, `logging/error_counter.py`)
— метрика строится на том, что код пишет `logger.exception`, то есть политика
логирования уже подразумевается де-факто.

План §16 задаёт пять вопросов к каждому вхождению и делает вывод: «Broad
exception допустим на boundary, где есть осознанная recovery strategy».
Нужно превратить это из рекомендации в зафиксированное правило.

## Решение

**Широкий `except Exception` разрешён только на явной operational-границе, где
есть осознанная стратегия восстановления и нормальное логирование. В остальных
местах он запрещён: ловится конкретный тип или перехват не ставится.**

Границей считается один из классов:

- **такт фонового цикла** (поллеры, планировщик, слушатели `LISTEN/NOTIFY`) —
  сбой шага логируется и цикл продолжается;
- **одна из многих независимых операций** (health-проверки, отдельная метрика) —
  падение элемента не роняет весь сбор;
- **публикация доменного события / outbox** — сбой откладывается в retry, а не
  откатывает уже совершённый бизнес-эффект;
- **программа-клиент внешнего сервиса** — недоступность отражается как факт
  (например, `{"available": false}`), а не как необработанный 500.

Правило по каждому вхождению (по §16):

1. Это operational boundary? — иначе заменить на конкретный тип.
2. Есть ли стратегия восстановления? — иначе нет права глотать.
3. Есть ли нормальное logging? — `logger.exception`/`exc_info=True`; молчаливый
   `pass` недопустим (кроме защиты логирования от самого себя).
4. Может ли ошибка скрыть programming bug? — если да, перехват сузить или
   добавить `raise`.
5. Нужно ли продолжать execution? — если нет, пробрасывать дальше.

Обязательные следствия для допустимых мест:

- **logging обязателен** (`logger.exception` с контекстом: что за такт/проверка).
- **голый `pass` запрещён**, кроме единственного исключения — самого механизма
  логирования/метрики, который не должен падать от собственного сбоя
  (`error_counter.py:41`).
- **сужение вместо `Exception`** там, где известен ожидаемый набор типов
  (`aiohttp.ClientError`, `asyncio.TimeoutError`, `json.JSONDecodeError`, ...).

Аудит проводится прицельно по 101 вхождению: сначала `pass`-глотания без
логирования и места без `exc_info`, затем — проверка вопроса №4 (скрытый
programming bug). Места, уже соответствующие правилу (поллеры, `web/app.py`
checks/metrics, outbox, `error_counter`), фиксируются как допустимые boundary и
не переписываются.

## Последствия

- **Плюсы:** единая формулировка «где можно широко ловить»; programming bugs
  перестают маскироваться под сбои; метрика ошибок остаётся полной, потому что
  логирование обязательно; меньше «но вроде же так безопаснее».
- **Минусы / цена:** разовая работа по аудиту 101 места; риск переусердствовать
  и сузить перехват там, где он был оправдан (для этого и нужны 5 вопросов).
- **Риски / что осталось открытым:**
  - Правило требует дисциплины на ревью: цель — чтобы «широкий `except`»
    требовал обоснования, а не появлялся по инерции.
  - Часть мест с `pass` (например, `main.py` pool-метрики) может намеренно
    остаться молчаливой — тогда это должно быть явно помечено комментарием с
    причиной, а не выглядеть как забытое.
  - Единый helper для фоновых циклов как таковой не вводится: наследование
    через `NewsPoller` (ADR-016) покрывает новостные трекеры, остальные границы
    остаются точечными.
