# Веб-панель: план реализации (от кода, не с нуля)

> Статус: план (код панели ещё не начат)
> Дата: 2026-07-18
> Отталкиваться от этого файла. Дополняет `WEB_PANEL_ARCHITECTURE.md` (принципы),
> но сверен с реальным кодом и недавними решениями (закалка конкурентности).

## Зафиксированные решения

- **Топология:** FastAPI — **отдельный процесс** (свой docker-сервис), а не в
  процессе бота. Изоляция; масштабируется независимо. Кэш настроек между
  процессами уже синхронизируется через Postgres `LISTEN/NOTIFY` (Фаза 3).
- **Структура:** `src/` бота **не рефакторим** в `apps/features`. Добавляем
  точку входа `src/api/` (FastAPI), которая переиспользует те же доменные
  сущности, use-case'ы и репозитории. Принцип «одна бизнес-логика» соблюдён без
  рискованного переезда 287 файлов.
- **Redis — НЕ сейчас.** Инвалидация настроек уже на `NOTIFY`. Сессии — через
  подписанный JWT в httpOnly-куке (без серверного стора). Redis вводим позже,
  только если понадобится кэш/пуш под музыкальную очередь (WebSocket).
- **Настройки — существующая `GuildSettings`.** Единая модель + `guild_settings`
  таблица + `SETTING_SPECS`/`KEY_KINDS` реестр уже есть и покрыты тестами.
  Панель переиспользует их, а НЕ плодит по-модульные таблицы (вопреки букве
  арх-дока — там дженерик-шаблон).
- **Модули панели — реальные фичи Поповы:** relationship (очки/роли/Единственный),
  music, cinema, finds, moderation, tempvoice, staykick, activity, ai. Никаких
  economy/marriage из шаблона.
- **Первый срез:** Discord OAuth2 + редактор пер-серверных настроек (`/config` в
  вебе). Причина: write-путь настроек уже закалён и протестирован (валидация +
  `pg_notify` + подхват ботом), поэтому срез проверяет весь вертикальный стек
  минимумом нового кода.

## Что берём из арх-дока как есть (принципы)

- Веб — второй клиент тех же UseCase; Discord и Web не знают друг о друге.
- API вокруг предметной области: `/api/guilds/{id}/settings`, а не `/set_volume`.
- Права проверяет ТОЛЬКО бэкенд; фронт только отображает ответ.
- Только Discord OAuth2, идентификация по Discord ID, без своих паролей.
- Фронт без бизнес-логики: формы, навигация, вызовы API.
- Feature-роутеры, без гигантского `api.py`.

## Архитектура API (отдельный процесс)

```
React (Vite, статик)  ──HTTP──▶  FastAPI (src/api, отдельный контейнер)
                                     │  reuse
                                     ▼
                          application use-cases  +  GuildSettingsService
                                     │
                                     ▼
                                 PostgreSQL  ──NOTIFY──▶  бот перечитывает кэш
```

- **DI:** отдельная лёгкая сборка `build_api_container(settings)` — НЕ тянет
  Discord-клиент, аудио-источник, AI-провайдеров, фоновые циклы. Нужны: engine +
  session_factory, `GuildSettingsService`, и по мере срезов — конкретные
  use-case'ы (для первого среза достаточно settings). Переиспользует
  `create_engine`/`create_session_factory` и существующие классы.
- **NOTIFY:** `GuildSettingsService.set/reset` в API-процессе уже шлёт
  `pg_notify` → бот подхватывает. Ничего доделывать не надо.
- **Живёт под тем же образом/зависимостями**, отдельный entrypoint
  (`uvicorn src.api.main:app`).

## Первый срез: OAuth + редактор настроек

### 0. Нужно от тебя (Discord Developer Portal)
- В приложении бота включить OAuth2, добавить redirect URI (напр.
  `http://localhost:8081/api/auth/callback`, потом прод-URL).
- Выдать **CLIENT_ID** и **CLIENT_SECRET** → в `.env`:
  ```
  DISCORD_CLIENT_ID=...
  DISCORD_CLIENT_SECRET=...
  WEB_OAUTH_REDIRECT=http://localhost:8081/api/auth/callback
  WEB_SESSION_SECRET=<длинная случайная строка для подписи JWT>
  WEB_ALLOWED_ORIGIN=http://localhost:5173   # фронт (CORS)
  ```
  (секреты — только в `.env`, в модель `GuildSettings` не идут.)

### 1. Авторизация (Discord OAuth2)
- `GET /api/auth/login` → редирект на Discord (`scope=identify guilds`).
- `GET /api/auth/callback?code=…` → обмен кода на токен, тянем `users/@me` и
  `users/@me/guilds`, кладём в подписанный JWT (httpOnly, SameSite=Lax) →
  редирект на фронт. Discord-токен не храним дольше, чем нужно для запроса.
- `POST /api/auth/logout` → чистим куку.
- `GET /api/auth/me` → кто я + список серверов, где я могу управлять.

### 2. Права (только бэкенд)
- Управлять сервером может тот, у кого в этой гильдии
  `MANAGE_GUILD` (0x20) или админ — из `permissions` в ответе
  `users/@me/guilds`.
- Плюс сервер должен быть тем, где **есть бот** (пересечение со списком гильдий
  бота). Иначе настраивать нечего.
- Проверка — в зависимости FastAPI (`Depends(require_guild_manager)`), на каждом
  `/api/guilds/{guild_id}/...`.

### 3. Эндпоинты настроек (тонкая обёртка над GuildSettingsService)
- `GET /api/guilds/{guild_id}/settings/schema` → форма из `SETTING_SPECS` +
  `KEY_KINDS` + дефолты/диапазоны (то же, что рисует `/config`-ког). Фронт строит
  форму по схеме, а не хардкодит поля.
- `GET /api/guilds/{guild_id}/settings` → текущее: `overrides()` поверх дефолтов
  (`resolved()`), с пометкой, что переопределено (`is_override`).
- `PUT /api/guilds/{guild_id}/settings/{key}` → `service.set(...)` (валидация
  поля + кросс-поле + `pg_notify`). Ошибку валидации отдаём 422 с человеко-
  читаемым текстом (у сервиса он уже есть).
- `DELETE /api/guilds/{guild_id}/settings/{key}` → `service.reset(...)` (вернуть
  дефолт).
- Списковые ключи (пороги/имена ролей и т.п.) — через `set_many` batch-эндпоинт
  (валидируются согласованно).

### 4. Фронт (React + TS + Vite)
- Страницы: **Login** → **Guild picker** (мои управляемые серверы) →
  **Settings** (форма по схеме, поля сгруппированы как в `/config`: модерация /
  отношения / AI / активность / кино / находки / музыка / каморки).
- Каждое поле знает тип (bool→switch, int/float→number+min/max, channel→селект
  канала, list/dict→спец-редактор), «сбросить к дефолту», индикатор
  «переопределено».
- Только отображение + вызовы API. Никаких правил.
- Дизайн — через установленный скилл `ui-ux-pro-max` (тёмная тема в стиле
  Поповы).

### 5. Деплой
- Новый сервис в `docker-compose.yml` под профилем `postgres`: `api`
  (`uvicorn`), порт 8081. Тот же образ/зависимости + fastapi/uvicorn/httpx.
- Фронт: в dev — Vite (5173) с проксёй на API; в прод — `vite build` в статик,
  раздаёт nginx или сам FastAPI (`StaticFiles`).

## Definition of Done (первый срез)
1. Захожу через Discord, вижу только свои управляемые серверы.
2. Меняю настройку в вебе → бот применяет её без рестарта (NOTIFY).
3. Валидация и права — только на бэкенде; фронт лишь показывает.
4. Тесты на OAuth, права, эндпоинты настроек зелёные на обеих БД.
5. Ничего не дублирует бизнес-логику: настройки идут через тот же
   `GuildSettingsService`, что и `/config`.

## Открытые под-решения (с рекомендацией)
- **Сессии:** JWT в httpOnly-куке (рекомендую) vs серверные сессии (Redis).
  Берём JWT — Redis не нужен.
- **Раздача фронта:** отдельный nginx vs FastAPI `StaticFiles`. Для старта —
  `StaticFiles` в том же контейнере (проще), позже вынести.
- **Где лежит фронт:** `web/` в корне репо (Vite-проект), рядом с `src/`.
- **Монорепа `apps/`:** пока НЕ вводим; `src/api` + `web/` достаточно. Пересмотр,
  если появятся ещё клиенты.
