# Подготовка к веб-панели: закалка конкурентности

> Статус: план (код ещё не тронут)
> Дата аудита: 2026-07-18
> Отталкиваться от этого файла при реализации.

## Зачем это

Веб-панель по замыслу ([WEB_PANEL_ARCHITECTURE.md](WEB_PANEL_ARCHITECTURE.md)) —
**второй клиент** той же бизнес-логики. Это делает систему **двухпроцессной**:
бот и веб-бэкенд пишут в одну Postgres одновременно.

Сегодня бот — фактически единственный писатель, поэтому паттерны
read-modify-write и check-then-act «безопасны» по факту. С панелью это перестаёт
быть правдой. Чинить после запуска панели — дорого (данные уже портятся в
проде), поэтому закаляем **до**.

Полный аудит проведён по всем 8 репозиториям (дважды, независимыми проходами).
Итог ниже.

|---|---|---|---|---|
| `RelationshipProfile.save` | full-row RMW | **порча данных** (потеря апдейта + затирание полей) | высокий (очки/заметки/заморозка) | 🔴 **HIGH** |
| Кэш guild-настроек | in-memory, не БД | бот не видит запись панели до рестарта | высокий (главная поверхность /settings) | 🔴 **HIGH** |

| `Playlist.save` | перезапись JSON-блоба | last-write-wins по имени | средний | 🟡 MEDIUM |
| «один активный на гильдию» (secret_room, movie_night) | check-then-insert, **нет** unique-индекса | два активных | низкий (бот-внутреннее) | 🟡 LOW-MEDIUM |
| votes / ratings / likes / playlist name | check-then-act, **есть** unique-констрейнт | `IntegrityError` (fail-loud, не дубли) | низкий (per-user) | 🟢 LOW |
| порог варнов | read-then-act | безобидный двойной мут | низкий (админ, редко) | 🟢 LOW |
| delete+add / delete-stale (диалоги, комнаты, баны, кики) | — | бот-внутреннее | нет | 🟢 LOW |

### Уже правильно (эталоны — брать за образец)
- `finds.claim_if_free` — атомарный `UPDATE … WHERE claimed_by IS NULL`.
- `album`, `voice_progress` — переведены на `INSERT … ON CONFLICT` (сессия 2026-07-17).
- «Единственный на гильдию» — защищён **частичным уникальным индексом**
  `uq_relationship_exclusive_per_guild` (двойного Единственного не будет даже под
  гонкой; худший случай — `IntegrityError`).
- moderation — только append + delete по ключу.

### Ключевой вывод
**Единственное место, где под двумя писателями реальна ПОРЧА данных (а не
fail-loud) — это `RelationshipProfile.save`.** Всё остальное либо отвергается БД
(unique-констрейнт/индекс), либо бот-внутреннее. Поэтому главный (и почти
единственный обязательный) заход — про relationship.

## Фикс #1 (HIGH): `RelationshipProfile.save`

### Суть проблемы
Use-case (`AwardPointUseCase` и ещё ~13) делают:
```
profile = get_or_create(user, guild)   # читают снимок
profile.points += 1                     # мутируют в памяти
save(profile)                           # ПЕРЕЗАПИСЫВАЮТ ВСЮ СТРОКУ из снимка
```
Два писателя на один профиль → последний `save` затирает чужой снимок целиком:
теряется не только счётчик, но и любое несвязанное поле (заметки, заморозка).
**Латентно уже сегодня** (два сообщения одного юзера подряд), панель делает
частым (админ правит очки, пока бот их начисляет).

### Варианты

**Вариант A — `SELECT … FOR UPDATE` (пессимистичная блокировка строки). РЕКОМЕНДУЮ.**
- В `get_or_create` читать строку с `.with_for_update()`. Конкурентный писатель
  блокируется до коммита первого, потом читает СВЕЖЕЕ значение.
- Точка внедрения ровно одна: `get_or_create` почти всегда = запись (все ~13
  write-путей идут через него), а `get()` остаётся для чтения без блокировки.
  Значит **не нужно** трогать 14 call-site — меняется один метод репозитория.
- «Единственного» НЕ локируем отдельно: его защищает частичный unique-индекс
  (fail-loud). Два одновременных перехода титула (разные юзеры) → второй упрётся
  в индекс → его начисление откатится. Редко и безопасно. Это снимает риск
  дедлока на двух строках.
- Плюсы: минимальная правка; сохраняет чистый паттерн get→mutate→save всего
  приложения; на SQLite `with_for_update` — no-op, а SQLite и так сериализует
  записи, поэтому тесты корректны.
- Минусы: блокировка держится до конца транзакции (транзакции короткие —
  ок); фоновые пути угасания/ДР идут не через `get_or_create`, а через
  list-запросы (`list_decayable`, `find_birthdays`) — их эта правка не покрывает
  (см. «Остаток» ниже).

**Вариант B — оптимистичная блокировка (колонка `version`).**
- `UPDATE … SET …, version=version+1 WHERE id=… AND version=:read`. rowcount=0 →
  конфликт → use-case перечитывает и повторяет.
- Плюсы: не держит локи; хорош при низкой контеншн.
- Минусы: миграция (колонка version); **логика повтора в каждом use-case**
  (перечитать + переприменить мутацию, для award_point — заново прогнать
  дневной потолок); кросс-строчная передача титула усложняет повтор. Инвазивнее.

**Вариант C — сузить запись до атомарных операций.**
- Вместо full-row save — точечные `UPDATE … SET points = points + :amount …`
  (как voice_progress).
- Плюсы: truly atomic, без локов и повторов, без затирания полей.
- Минусы: самый инвазивный — ломает паттерн «доменный объект → save» по всему
  relationship; дневной потолок в SQL — CASE-выражения; передача титула всё
  равно кросс-строчная. Большой рефактор.

### Решение (зафиксировать перед кодом)
**Вариант A.** Причина: чинит реальную порчу минимальной правкой, не задевая
архитектуру, а edge-кейс «Единственного» уже прикрыт индексом (fail-loud).
Если понадобится — B/C можно добавить точечно позже.

### План реализации A
1. `IRelationshipRepository.get_or_create` — читать через
   `select(Model).where(pk).with_for_update()` вместо `session.get`.
   `get()` (чтение) не трогать.
2. Проверить, что identity-map репозитория не отдаёт незалоченный кэш там, где
   нужен лок (первый `get_or_create` в транзакции должен реально взять лок).
3. Тест-регрессия в `tests/test_concurrency_postgres.py` (только Postgres):
   N параллельных `AwardPointUseCase` на одного юзера → `points == N`.
   ДО фикса тест падает (доказать баг мутацией/старой версией), ПОСЛЕ — зелёный.
   Плюс тест: бот-award ∥ web-set-points не теряет админскую правку.
4. Полный прогон на SQLite и на Postgres (`TEST_DATABASE_URL`).

### Остаток (вторично, после A)
Фоновые пути пишут профиль не через `get_or_create`, а через list-запросы:
- `DecayPointsUseCase` (`list_decayable` → mutate → save) — раз в несколько дней,
  бот-внутреннее.
- `BirthdayTickUseCase` (`find_birthdays`) — раз в день.
Веб-контеншн низкий, но если админ правит очки во время угасания — потеря
апдейта. Решение при желании: те же строки читать `with_for_update` в
list-запросах угасания, либо перевести списание на атомарный `UPDATE … SET
points = points - :n`. **Не блокер для панели.**

## Фикс #2 (HIGH): кэш guild-настроек

### Суть
`GuildSettingsService` держит настройки в **памяти** (грузит при старте +
обновляет на СВОИХ `/config`). Запись в БД защищена (`uq_guild_setting`), но
если панель пишет настройку в БД — **бот не узнает** до рестарта. Это не гонка
строк, а межпроцессная инвалидация кэша.

### Варианты
- **Postgres `LISTEN/NOTIFY`** — бот слушает канал, панель шлёт `NOTIFY` при
  записи настройки → бот перечитывает ключ. Без новой инфраструктуры (только
  Postgres). Рекомендую как первый выбор.
- **Redis pub/sub** — как в исходном арх-доке; оправдан, если Redis всё равно
  появится под кэш/сессии панели.
- **Периодический reload** — проще всего, но лаг и лишние запросы.

### Решение
Отложено: тесно связано с выбором Redis vs NOTIFY, а он зависит от того, будет
ли Redis в стеке панели вообще. **Решать вместе с началом бэкенда панели.** До
этого момента панель настройки писать не должна (или писать + принудительный
reload сигнал).

## MEDIUM (по желанию, не блокеры)
- `MovieEntry.save` / `MovieNight.save` — тот же full-row RMW, что relationship,
  но холодный. Тот же приём (Вариант A: `with_for_update` в `get`/write-путях)
  ляжет по образцу relationship. Делать, если панель даст управление киноклубом.
- `Playlist.save` — перезапись блоба. Если панель даёт редактор плейлистов —
  перевести на «прочитать под локом» или версионирование. Иначе last-write-wins
  по имени приемлемо.

## LOW (принятый риск — НЕ чинить сейчас)
- votes / ratings / likes — fail-loud (unique-констрейнты). Перевести на
  `ON CONFLICT` оппортунистически, только если станут веб-поверхностью.
- «один активный на гильдию» (secret_room, movie_night) — редкие бот-действия;
  добавить unique-индекс, только если панель даст «запустить» эти сущности.
- порог варнов, delete+add бот-внутренних — оставить.

## Приложение: как проверять конкурентность (шаблон)
Тесты гонок гоняются только на Postgres (SQLite сериализует записи), через
`asyncio.gather` отдельными задачами (ручное чередование в одной корутине
дедлочит под FOR UPDATE). Образец — `tests/test_concurrency_postgres.py`
(`test_voice_accrual_correct_under_concurrency`: N параллельных инкрементов = N).
Строгий тест: доказать мутацией, что старый код падает, а фикс — нет.
